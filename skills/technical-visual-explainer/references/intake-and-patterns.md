# Brief and diagram selection

Read before choosing a form for an ambiguous request. Do not use the questions as a compulsory interview.

| Missing decision | Ask in practical terms |
|---|---|
| Purpose | Where will the figure appear, and what should the reader understand? |
| Audience | What does this audience already know? |
| Structural question | Are we explaining the order, the parts and boundaries, why something happens, or differences between alternatives? |
| Sequence | One overview, or the same map with progressive close-ups? |
| Appearance | Which supplied reference should determine style? White or dark? |
| Fidelity | Which connections and distinctions must remain exact? |

Collapse these into at most three questions when several are missing. Use options only when they express real choices. A supplied audience, format, reference and scope are enough to begin. A minor label correction does not justify re-eliciting the full brief.

## Match form to relationship

| Understanding task | Form | Preserve |
|---|---|---|
| What happens next? | Workflow | order, branches, terminals, returns |
| What is built on what? | Layered architecture | containment versus use/dependency |
| How does the component work? | Detail loop | input, operation, check, output, meaningful retry |
| How do alternatives differ? | Parallel lanes | shared comparison basis, actual convergence |
| How does A change B? | Mechanism/coupling | causal direction, units/interfaces, feedback timing |
| How are concepts related? | Hierarchy or relationship map | relation labels; no invented execution order |
| How does a measured quantity change? | Standard data plot | real data, axes, units, uncertainty |

Do not impose physical-model nodes on an agent workflow or quality gates on a taxonomy. Data plots route to scientific plotting and may be used unchanged within a broader explanation.

## Minimal working record

Purpose and audience; one message; supplied evidence; exact visible labels; nodes with roles/status/parent boundary; directed connections with conditions; view sequence; palette; exclusions; output destination. A small diagram may need only a few sentences. Large families need stable object IDs so renaming and handoffs can be checked across views.

For a current system versus proposed change, mark present components from verified sources. Unverified capability claims remain proposed or unresolved. Avoid inventing new components just to fill a template.
