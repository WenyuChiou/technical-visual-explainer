# Progressive overview-to-detail families

## Establish a stable master

Write a stage registry with stable IDs, labels, icons and order. Overview contains only the complete high-level path, genuine containment/dependencies and named entry/exit. No hidden claim that future steps have already run.

Add each icon's functional subparts and colors to that registry, with named counterparts in the detail. A stage is not a single role: use its number/name/shape to recognize it, and component color to recognize what kind of work or information it contains. The master needs only short stage names, key elements and meaningful interconnections. Move detailed operations and checks into zooms; move explanatory sentences into speaker cues or external captions. A zoom still uses labels, not a paragraph explaining the stage. For a research layer on Codex, keep the existing Codex harness as the common foundation in the master and preserve that interpretation in every detail.

Use the same navigation map in the same location in each detail view. Apply the conditional legend rule in [visual-grammar](visual-grammar.md): a readable map does not require a repeated legend. If needed, keep the key unobtrusive and semantically consistent. Reserve a stable expansion area. A navy current-stage outline is the default focus cue; inactive stages retain their category colors and readable labels. Preserve recognizable colored icon parts in the expansion. A short “Future work” or “Case ends here” label describes scope independently; explain the limitation outside the diagram. Do not desaturate colors needed for category decoding.

Keep the legend's proportion subordinate as well as its meaning stable. When a master needs an editable companion, retain stage IDs, icon identities, object names and attached connectors in that companion. After a layout change, check both the master and affected detail views; linked names or positions do not synchronize automatically unless the actual file mechanism supports and passes that test. See [editable-companions](editable-companions.md).

One page can highlight a group only if its internal relationships remain legible. When several stages each have their own checks and branches, give each stage a detail view. A taxonomy or architecture may instead reveal layers; do not manufacture stage numbering.

For imagegen-only output, generate and inspect the overview first, then an initial detail view. Use the accepted detail layout as the reference for subsequent peers and carry the exact stage registry into every prompt. Prevent position drift with the same canvas regions and named anchor objects. Small pixel differences are expected; swapped positions, changed names or arrows are not.

## Checked loop semantics

Typical loop: input → operation → tool/evidence → check. PASS reaches a named output. REVISE reaches the correction point, then returns through the check. HUMAN reaches a specific decision or explicitly labeled wait/stop.

A human path need not always lead to success. If evidence remains inadequate, retain an unresolved terminal. Do not change acceptance criteria merely to make a loop pass. Records can be attached to the relevant operation, but cannot route a failure around a check.

Some stages require mandatory human selection after automated screening; put that selection on the main accepted path, separate from escalation. For example, topic suitability checks screen options but do not replace the researcher's final choice.

Use cross-stage return targets by their stable names. Do not draw a vague “back” arrow. A current case can stop at planning while the architecture still describes later execution and writing.

## Pointing sequence

For each detail view: locate the active stage on the master; identify what it receives; follow the work and tool path; read the check; trace success, correction and unresolved/human outcomes; name what is handed onward. Include the risk it addresses only when that risk is supported by the brief.

An overview plus zooms is a visual sequence, not proof that the software implements the whole graph. Proposed and future processes remain labeled as such.
