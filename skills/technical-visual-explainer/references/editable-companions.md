# Editable companions after image generation

Use this reference when editable delivery is requested. Reuse the known output editor and edit scope; ask only consequential missing choices. Distinguish text changes, icon/module moves, branch edits and simple resizing.

## Preserve the primary generation route

When the brief retains imagegen, generate and inspect the complete master first, then add an editable companion. Preserve the master, prompt and confirmed tool metadata. Do not claim that imagegen returned native layers or a verified model version unless the tool exposes it. An explicit native-only request may use another authoring route.

Choose the companion from the actual picture. Text/shape/arrow diagrams suit semantic reconstruction with native labels, shapes and attached connectors. Generated icons can remain separate movable raster images, preserving their colored appearance; their internal pixels are not editable vector parts. When extraction is needed, use supported editing/extraction tools and inspect the result. Never leave old labels or arrow fragments baked into movable images. A whole-page bitmap is a reference slide, not editable layout.

A supported image-to-design service is another option, but inspect the actual converted objects and exported file. Tool advertising, a successful upload, or a file extension proves none of these capabilities. If conversion fails, report the result and use an authorized alternative without silently replacing the primary imagegen master.

## Declare what is editable

For each relevant category, record what is actually delivered: native text; formatted formula text or equation object; node/group; attached connector; independent edge label; movable raster icon; whole-page reference; named alias. Semantic reconstruction does not recover original image layers or identify the source font.

Keep stage IDs, names, icon meaning and endpoints tied to the content map. Group a node's icon and label when the target editor supports useful group moves. Do not turn shared platform support into a serial stage or turn a source-supported panel dependency into invented internal connections.

## Preserve the master's appearance

An editable companion follows the supplied master's design unless the user asks for a redesign. Do not apply a new template, shrink its legend, delete separators or change typography merely to simplify reconstruction. If redesign is requested, label that output separately; do not modify the reference to conceal a mismatch.

Before reconstruction, record a compact visual map from the actual master:

- Canvas ratio and major bounding boxes; outer frames, panel fills, corner radii, gutters, separators and legend partitions.
- Text positions, hierarchy, line breaks, alignment, visible glyph height/width and weight. Use known source fonts when available. A raster image rarely identifies a font: compare installed candidates, select a close substitute and record uncertainty. Do not shrink or clip labels to hide a poor font match.
- Icon crops and proportions; line widths, dash patterns, arrowhead sizes and attachment positions. Preserve meaningful styles and distinguish structural dividers from workflow edges.

Build on the same coordinate system, or use a uniform documented scale. Inspect the baseline rendered by the target editor against the unchanged master at the same dimensions. Use aligned side-by-side views and, when helpful, an overlay or comparison crops. Check the whole composition plus frames, longest labels and key joins. A global pixel score mixes font rasterization and image texture with layout defects; it cannot replace this inspection.

Treat missing frames/dividers, shifted modules, changed line breaks, visibly mismatched text hierarchy and distorted icons as unresolved fidelity defects even if all objects are editable. Correct those defects before calling the companion faithful. Report remaining font/texture differences specifically; a blanket “not pixel-identical” disclaimer does not excuse omitted design elements. Keep appearance fidelity, semantic correctness and editing behavior as separate verdicts.

## Test editing, not only packaging

On a separate copy, change a label, move a representative module and decision, modify/restore a formula if present, and reconnect/restore an edge. Save, close, reopen and render. Check endpoint identity AND connection site, arrow direction, bypasses, branch labels and crossings. Record the actual editor and tested move scope; small moves do not prove arbitrary automatic layout.

Inspect the generated master, native baseline and edited rendering separately. Verify requested colored icons survived reconstruction, the legend follows the master and remains readable, and no stale raster text or line remains. Identify labels/aliases that require manual repositioning or synchronization. If an attached port is needed to preserve an arrow's position, group it with its actual owner and test that move. Do not infer another editor's behavior from valid XML or a passed PowerPoint test.

Deliver the master, companion, concise edit instructions and honest QA status. For a progressive family, check affected overview/detail correspondence after edits. Preserve rejected attempts as historical evidence when needed, and distinguish technical editability from scientific fidelity and the user's design acceptance.
